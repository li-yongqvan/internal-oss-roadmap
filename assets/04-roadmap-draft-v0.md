# 内部开源社区建设路线图

> **v0.1 草稿**（04 号原型票产出，待运营者反馈后定稿为 v1）。【待确认】标记处为提议稿，请直接批注。
> 准绳：运营者仅 1 人兼职；粗糙可用优先（v0.1 精神）；一切机制以"单人可运营"裁剪（见 02 号资产）；阶段为相对阶段，不绑定日历。

## 0. 目标与成功标准

**一句话目标**：在 1 名兼职运营者的人力约束下，建起一个内部开源社区，让工程师在公司内部经历真实开源协作（公开仓库、code review、阶梯认可），培养出首批开源人才。

**成功标准（提议稿，按阶段退出条件计，不按日历）**：

| 时点（参考值） | 达成即算成功 |
|---|---|
| P0 退出（约 4–6 周） | 1 个种子仓库；≥2 名非本团队成员各完成 ≥1 个合并 PR；机制文件四件套入库；月度盘点 ≥2 期；运营耗时 ≤3h/周 |
| P1 退出（约 2–3 个月） | 2–3 个活跃仓库；≥1 名 Trusted Committer 独立承担 review ≥1 个月；good first issue 每周稳定供给 1–2 个；月报连续 3 期未断 |
| P2 退出（约 6 个月后） | 10–30 人参与；≥2 名 TC；机制升级触发条件执行过 ≥2 项；有共同发起人或明确的运营者备份方案 |

【待确认】以上阈值（2 人 / 3 仓库 / 10–30 人）是否贴合你的实际团队规模，偏严或偏松请直接改。

**运营时间预算**（路线图是否可执行的硬约束）：

- 六机制日常：2–2.5h/周（02 号资产逐项核算）
- 月度盘点 + 月报 + 公开表扬：0.5 天/月（03 号资产 L1 档）
- 平台运维 + 答疑：约 0.5h/周（自建 Gitea 时）
- **合计约 3–3.5h/周，<10% 工时**。Bosch 教训（02 号资产）的 30% 警戒线约 12h/周，总量安全；真正的风险是碎片化而非总量——所有任务都设计成固定时段执行（见风险 R1）。

## 1. 阶段规划

### P0 冷启动（约 4–6 周）

**目标**：让第一位外部贡献者完整走通"认领 good first issue → 提交 PR → 72h 内 review 合并 → 公开表扬"闭环，并让这套机制在无运营者盯梢时也能自行运转一周。

**进入条件**：无（今日即可启动）。**前置拍板**：D1 平台（第 2 周前）、D5 种子仓库（第 1 周）。

**任务分解（单人可执行）**：

- **第 1 周：拍板与备料**
  - [ ] 问 IT/平台管理员：公司 GitLab 能否开顶级组、可见性能否设 internal → 据此拍板 **D1**（半天）
  - [ ] 按 **D5** 标准挑定种子仓库，从其 backlog 拆出 5 个候选 good first issue（首批 gfi 来源 = 你自己团队待办里"有人要、边界清、2 周内可完成"的任务：文档补全、小 bug、测试补充、脚本工具化）
  - [ ] 确认 **D2/D3/D4**（三张研究票已给推荐默认项，实际动作是过目确认，约 30 分钟）
  - [ ] 写机制文件初稿（与平台无关，纯文本可先写）：README 社区定位一段、CONTRIBUTING（含 72h lazy consensus、两级阶梯、gfi 认领方式）、行为准则（Contributor Covenant 中文版 + 自定义 reporting 段）、issue/PR 模板（含大改动 4 节提案模板）、CODEOWNERS/OWNERS
- **第 2 周：上架与邀请**
  - [ ] 建 inner-source 组 + 种子仓库，机制文件入库，可见性 internal
  - [ ] 挑 2 个候选 gfi 打标签、写清验收标准（每周 30 分钟例行，固定周二）
  - [ ] 建月度盘点表（03 号资产 L1 模板）
  - [ ] 私下 1:1 邀请 2–3 位潜在首批贡献者：优先从协作过的同事开始，话术落在"有个 30 分钟能做完的具体任务"而非"加入社区"
- **第 3–4 周：首贡献闭环**
  - [ ] 结对带第一位贡献者：每周一次 30 分钟 1:1 + 指定 1 个入门任务（首期导师 = 运营者本人，02 号资产结对影子模式；TC 诞生后分担）
  - [ ] 所有 PR/issue 72h 内响应，gfi 被认领当天回复
  - [ ] 留意 lazy consensus 是否真的在跑（大改动提案有没有人看、有没有人反对）
- **月末：例行化起点**
  - [ ] 第一次月度盘点 + 月报（社区公开贴 + 抄送主管）+ 公开表扬首位贡献者
  - [ ] 复盘运营耗时是否 ≤3h/周、机制哪条最费时 → 决定进 P1 或延长 P0

**第一个周末就能做的事（最小可行动作，无需等任何人回复）**：
1. 写机制文件四件套初稿（纯文本，与平台无关）；
2. 列 3 个种子仓库候选 + 各 5 个候选 gfi；
3. 给 IT 发 GitLab 可用性询问（工作日等回复）。

**退出条件**：≥2 名非本团队成员各完成 ≥1 个合并 PR；机制跑满 4 周；运营 ≤3h/周；月度盘点 ≥2 期。

### P1 试点（约 2–3 个月）

**目标**：从"1 个仓库的实验"变成"可复制的套路"：首位 TC 诞生并实际分担 review，冷启动四步（机制文件 + 5 个 gfi + 1:1 邀请 + 月报）被复制到第 2、3 个仓库。

**进入条件**：P0 退出条件全部达成。

**任务分解**：

- **TC 评选与放权**：贡献满约 4 周、≥5 个已合并 PR 者公开邀为 Trusted Committer（给 review + 合并权，晋升 = 群里一句话 + OWNERS 文件更新）；**把 review 放出去是运营者自保的第一优先**（02 号资产 30% 红线教训）
- **仓库扩展**：按三条标准选第 2、3 个仓库——有第二个消费团队 / 有复用价值 / 原 Owner 有意愿；每个新仓库复制 P0 四步冷启动套路，目标每仓 ≥1 名非运营者贡献者
- **导师分担**：TC 开始结对带新人，运营者从前几对 1:1 退到旁听
- **认可例行化**：月报固定化；做一次 15 分钟内部分享（社区案例）；继续公开表扬
- **每月末过一遍 02 号资产升级触发条件**，触发才升级、不提前建设：
  - ≥3 名新人找不到任务或候选池 >20 → 上 label bot + 看板
  - 同期 open 提案 ≥3 或出现跨部门冲突 → 引入 RFC 目录 + 状态页
  - review 排队 >1 周 → 加 Reviewer 层
  - 参与者 >20 → 行为准则设 2–3 人执行组

**退出条件**：≥1 名 TC 独立承担 review ≥1 个月；2–3 个仓库各有 ≥1 名非运营者贡献者；月报连续 3 期；运营仍 ≤3h/周。

### P2 扩展（6 个月起，转入常态运营）

**目标**：10–30 人参与规模，机制按触发条件完成第一轮升级，可持续性不再依赖运营者一人。

**进入条件**：P1 退出条件全部达成。

**任务分解**：

- **机制升级**（对应 02 号资产"10–30 人"档）：good first issue 自动化、RFC 目录页、CoC 执行组；度量评估升 L2（API 脚本拉数，03 号资产）——仅在"需要向管理层证明 ROI"或项目数明显增长时做
- **激励升级评估**（D4 复议）：徽章/游戏化（有发放渠道后）；兑现成长机会——外部大会名额、转岗/轮岗任 TC 的通道（需管理层支持，月报的团队级指标是铺垫）
- **可持续性硬任务**：找到共同发起人或明确运营者备份（TC 中培养），运营者可休假两周而社区不停摆
- **占位（超出本路线图范围，出现需求再议）**：对外开源（CLA/法务/合规评估）

**退出条件**：无"退出"——转入常态运营；若运营耗时突破 12h/周（30% 红线）或连续 2 个月月报断更，触发重规划而非硬扛。

## 2. 决策点清单

> 每项含推荐方案、选项对比、决策标准、最晚决策时间。详情见对应研究资产。

### D1 平台选型（详情：01 号资产）

- **推荐**：优先挂在公司已有 GitLab 实例开 inner-source 顶级组（零新增基础设施）；无实例则自建 Gitea（最低 2 核 1 GB 可跑，推荐 2 核 4 GB + 1 个 act_runner 跑 CI，半天上线）
- **选项对比**：公司 GitLab（上手≈0，但免费版缺 CODEOWNERS 强制审批与贡献统计，勿被"买 Premium $29/人/月"绑架）/ 自建 Gitea（极轻，机制覆盖够用，缺分析面板）/ GitHub 云（机制最全，但国内访问与合规硬伤，不作默认）
- **决策标准**（按序）：① 公司已有 GitLab 且有闲置容量 → 用它；② 代码必须留内网 → 排除 GitHub 云；③ >50 人且需贡献看板 → 才评估付费档
- **最晚决策时间**：**第一个试点仓库创建之前**（P0 第 2 周前）——机制文件与平台绑定，中途迁移成本高

### D2 机制取舍（详情：02 号资产）

- **推荐**：六机制 MVP 全套（两级阶梯 + 人工 gfi + 结对导师 + 72h lazy consensus 两档提案 + Contributor Covenant + 月度盘点），合计 2–2.5h/周
- **选项对比**：K8s 式全套（四级阶梯/SIG/KEP 状态机——个位数参与者下层级空转，裁掉）/ MVP 六机制（当前推荐）/ 极简（连提案流程都不要——跨仓库改动出现后会有利益冲突，不建议）
- **决策标准**：单人 ≤2.5h/周可运营；每条机制在个位数参与者下不空转；每条都有写明的升级触发条件
- **最晚决策时间**：P0 第 1 周写机制文件时（即"现在"）

### D3 度量（详情：03 号资产）

- **推荐**：L1 手工月度盘点——每月 0.5 天，从平台自带统计抄录：活跃贡献者数、已合并 PR 数、gfi 完成率、复用项目数、人才流向，发月报 + 公开表扬
- **选项对比**：L1 手工（起步首选）/ L2 半自动（API 脚本，1–2 天搭建，20–50 项目再上）/ L3 自动（GrimoireLab 等，需专人，>50 项目才考虑）
- **决策标准**：能回答"谁在贡献、趋势如何、人才去了哪"即可；不为度量而度量
- **最晚决策时间**：P0 第一次月度盘点前；升级触发：项目 >50 或跨多平台

### D4 激励（详情：03 号资产）

- **推荐**：公开认可（月报表扬、案例分享）+ 成长机会（大会名额、转岗 TC）为主线；绩效挂钩只做团队级指标 + 主管定性评价，**勿直连个人 commit 数与薪酬**（Goodhart 风险）
- **选项对比**：公开认可（零成本，全阶段）/ 徽章游戏化（有量之后，防贬值）/ 排行榜（刷量风险最大，谨慎）/ 绩效挂钩（团队级 + 定性才有保护）/ 物质奖励（挤占内在动机，仅事件性少量）/ 成长机会（最可持续，需管理层支持）
- **决策标准**：不诱发刷量；不挤占内在动机；单人可执行
- **最晚决策时间**：首次公开表扬前（P0 月末）；徽章/物质留到 P2 复议

### D5 种子仓库选择

- **推荐**：从你自己维护、最熟悉的项目里挑第一个
- **选项对比**：自己维护的项目（冷启动最快，gfi 供给有保证）/ 他人维护的热门项目（需求真实但 Owner 意愿未知，放 P1）/ 为社区新起的项目（"简历项目"风险：无真实消费者，不建议）
- **决策标准**：真实需求（有人等着用）；边界清晰（新人 2 周能上手）；Owner = 你自己；能拆出 ≥3 个 good first issue
- **最晚决策时间**：P0 第 1 周

## 3. 度量

- **档位**：L1 手工月度盘点（当前，详见 D3）；字段：活跃贡献者数、已合并 PR 数、gfi 完成率、复用项目数、人才流向
- **节奏**：每月最后周五 0.5 天：抄数 → 写月报（公开贴，模板固定：本期数字 / 表扬名单 / 下期 gfi 预告）→ 抄送主管
- **度量回答的三个问题**（回答不了的字段就删）：社区在长大吗？谁在持续贡献？人才流向了哪里（含转岗 TC）？
- **升级触发**：项目 >50 或跨多平台 → 评估 L2/L3（03 号资产）；需向管理层证明 ROI → 同上

## 4. 风险

| # | 风险 | 等级 | 缓解 |
|---|---|---|---|
| R1 | **运营者单点与倦怠**（Bosch 教训：投入 50%→30% 后贡献枯竭） | 高 | 总量预算 ≤3.5h/周并写死；任务固定时段执行（周二挑 gfi、月末盘点），防碎片化；月报即公开承诺；**放权给 TC 是第一优先**；P2 硬任务：共同发起人；连续 2 周无法投入 → 发"维护模式"公告而非静默消失 |
| R2 | **响应迟缓杀死贡献热情**（内部贡献者没有开源者的耐心） | 高 | 72h 内响应写进 CONTRIBUTING 并自我遵守；review 排队 >1 周 → 立即加 Reviewer 层（02 号触发条件） |
| R3 | 种子项目无真实需求，贡献无人合并（自嗨） | 中 | D5 决策标准前置过滤；首个 gfi 必须来自真实 backlog 而非"为社区造的任务" |
| R4 | 机制空转（提案没人看、阶梯没人用） | 中 | lazy consensus 替代投票；两级阶梯；一切升级等触发条件，不提前建设 |
| R5 | 管理层可见性不足，成长机会无法兑现 | 中 | 月报固定抄送主管；只用团队级指标；若 6 个月后仍无管理层认可，激励退守纯公开认可，不做绩效挂钩 |
| R6 | 被 GitLab Premium 功能诱惑绑架（$29/人/月） | 低 | D1 决策标准提前写死；免费版替代方案已在 01 号资产 |
| R7 | 未来对外开源引入 IP/合规问题 | 低 | 当前全部内网，out of scope；对外需求出现时先做 CLA/法务评估（P2 占位） |
